# 视频上传 v0.1：需求与验收

日期：2026-11-15。用户已要求开始编码。本文维护产品行为；技术实现以 technical-notes.md 和代码为准，验证结果由 tasks.md 维护。

## 已确认的范围

- 本地单用户使用，无登录和用户隔离。
- 先实现视频上传，对齐简历中的分片上传、已上传分片复用与中断后续传；字幕总结闭环及 Agent 暂缓。
- 使用分片上传；每个分片成功后记录成功序号。每轮开始前查询服务端进度，仅传缺片；本轮所有请求结束后再进行下一轮补传。
- 刷新页面后，重新选择同一份原文件，仍可继续原上传，复用成功分片。
- 后续可以找回已保存视频；上传过程与已完成资产需要分开定位。初始化重试返回同一上传会话，完成重试返回同一资产。
- 只有最终文件存储和数据库保存均成功后，才显示视频上传成功。分片齐全不等于最终保存完成。

## 开发暂用边界

以下为本次落地所用的可调整开发值，不是用户指定的永久产品限制，也不是性能验证结论：

| 项目 | 当前暂用值 |
| --- | --- |
| 文件选择 | MP4、WebM、MOV；按声明的类型接收，不验证编码可播放性 |
| 单文件上限 | 2 GiB；未验证该大小文件的真实上传 |
| 每片大小 | 5 MiB，末片按实际剩余大小 |
| 补传 | 每次操作最多 3 轮，每轮前重新查进度；用尽后可手动继续 |
| 前端在途请求 | 最多 3 个；每个请求超时 60 秒，轮间等待 1 秒 |
| 续传期限 | 24 小时，成功分片后续期；到期明确提示重新开始 |
| 部署与列表 | 单后端实例；页面列出最近 100 条资产，按资产编号读取仍独立可用 |

## 用户流程

选择原视频 → 核对文件内容 → 创建或找回上传会话 → 分轮上传缺片 → 校验、合并与保存 → 显示已保存资产。

刷新后：重选原文件 → 找回原会话 → 查询成功序号 → 只补缺片。已完成后：从视频列表打开原资产，不需要原文件，也不需要再次上传。

失败时保留本地会话定位信息。查询进度失败不能按零进度重传；保存失败不能报成功；过期会话不悄悄创建新任务，用户必须明确选择重新开始。

## 验收标准（实现不等于全部实测通过）

| 编号 | 场景与预期 |
| --- | --- |
| U01 | 连续点击与初始化响应丢失后重试，仍使用同一请求键和上传会话；同键换文件应拒绝。 |
| U02 | 一轮中部分分片失败，其他分片仍可结束；下一轮查询后只补缺片，不重传服务端已确认的部分。 |
| U03 | 上传部分分片后刷新页面，重选原文件继续同一会话；不同内容不能混入原会话。 |
| U04 | 对象写入失败不记录成功序号；响应丢失后根据服务端进度继续，不仅依赖前端失败列表。 |
| U05 | 分片校验或合并失败、最终对象写入失败、数据库保存失败时，不显示已保存成功，允许合理重试。 |
| U06 | 重复完成返回同一资产；刷新和重启后能从数据库读回同一记录，读取不依赖临时 Redis 上传状态。 |
| U07 | 视频列表能打开或下载已保存对象；范围读取内容正确，对象缺失或存储不可用时不虚构成功读取。 |
| U08 | 会话过期时明确提示；临时数据清理不删除已完成视频，清理失败可再次处理。 |
| U09 | 上传服务未启用时页面显示真实配置状态，不允许发起假上传。 |

2026-11-16 已使用真实 MySQL、Redis、MinIO 和浏览器验证约 12.5 MiB、3 片 WebM 的上传、刷新重选续传、注入请求失败后的按轮补传、重复初始化与完成、下载及播放。应用重启后，全新浏览器仍能读取同一资产。失败注入、可控测试和真实服务的具体证据分别记录在 tasks.md；这不代表 2 GiB 性能或所有异常均已在真实环境实测。
